# head-session: spawn в любом проекте и привязка чужих сессий

Дизайн от 2026-11-12, обсуждён со Стасом в сессии head-session-auto-head (8be5f386). Продолжение [2026-11-11-claude-wt-head-zones-design.md](2026-11-11-claude-wt-head-zones-design.md).

## Зачем

Две проблемы, на которые Стас наткнулся при работе head-сессий.

1. **Spawn не открывает ребёнка в чужом проекте.** Head из ExpertizeMe (`/home/popstas/projects/text/obsidian/ExpertizeMe`) попросил ребёнка в `/home/popstas/projects/js/amnezia-shared-panel` и получил 403: менеджер пускает только `cwd`, который точным совпадением есть в `claudeWt.projects` (`src/claude-wt/session-new-helpers.js:94`). Head часто ведёт проект в одном репо, а задачу отдаёт в другой. Слова Стаса: "запрет на spawn не по проекту, где открываем, а по родительскому проекту".
2. **Исполнители, которых head не создавал, ему не дети.** В `/head-session @a @b` исполнители уже живые сессии. Пикер не показывает их детьми head, Ctrl+Win+F10 не кладёт их в группу, session-close их не закрывает. Слова Стаса: "head-session должен привязывать упомянутые сессии как детей, которые не создавал".

## Цели

- Spawn проходит, если проект **head** есть в `claudeWt.projects`, а каталог ребёнка - внутри `~/projects` на pc-virt.
- Head привязывает названных исполнителей детьми. После привязки (Стас):
  - пикер показывает их детьми head;
  - head может их закрывать через session-close;
  - Ctrl+Win+F10 кладёт их в одну группу со спавненными.
- Иерархия head разрешена: ребёнок может сам быть head и иметь детей (Стас).
- Привязка сессии, которая уже чья-то дочка, меняет ей родителя (Стас).
- Ctrl+Win+F10 на сессии посередине (ребёнок A и head своих детей) раскладывает **её собственную** группу с её детьми (Стас).

## Не цели

- Авторизация маршрута `session-new`. Он остаётся без пароля, защита - белые списки.
- Автоматическая привязка без head-session: привязывает только head, явно.
- Новый вид отображения в пикере: дерево уже показывает любую глубину (`session-tree.js:44-115`).

## Антицели

- Маршрут `session-new` пускает агента в произвольный каталог машины. Корень `~/projects` - граница.
- Привязка двигает окна. Окна стоят, где стоят, до хоткея (как решение Стаса 11.11 про закрытие ребёнка).
- Закрытие привязанной сессии без явного "да" Стаса на конкретную сессию. Правило session-close прежнее.
- Цикл в иерархии: группа или дерево ходит по кругу.

## Как устроено сейчас

- **Менеджер** (`session-new-helpers.js` `parseSessionNewRequest`): `cwd` обязателен, точное совпадение с `claudeWt.projects[].cwd`, иначе 403. Профиль терминала - `profileForTerminal(cwd, ...)` (`project-helpers.js:92`), тоже по точному совпадению `cwd`. Трекер окон `~/.ccfzf/windows/<host>.json` хранит `windows[sid]` = title, desktop, monitor, zone, slot, без каталога сессии. Группы для раскладки менеджер берёт только из запроса (`claude-layout.js:283` → `group-layout.js`), записи heads/children не читает. Свой реестр детей `child-registry.js` пишет `session-new`, читает подсчёт мест в зоне (`child-place.js:127`).
- **Записи на pc-virt:** `~/.ccfzf/heads/<sid>.json` (метка head: sessionId, name, cwd, createdAt) и `~/.ccfzf/children/<sid>.json` (sessionId, name, head, headId, cwd, createdAt).
- **Скиллы** (`~/.claude/skills`), одноуровневое правило зашито здесь:
  - `head-session/head-mark.mjs:25-30` отказывает сессии с записью ребёнка ("head быть не может");
  - `head-session/SKILL.md:12` на этот отказ велит не начинать проект;
  - `session-spawn/spawn.mjs:52-53` отказывает, если вызывающий - ребёнок;
  - `session-close/close.mjs:44` то же; `:53-57` закрывает только при `child.headId === me`; `:61` busy без `--force` не закрывает;
  - `session-find/find.mjs` записи только показывает.
- **Агрегатор ccfzf** (`~/projects/shell/ccfzf`, копия в `ccfzf-picker/vendor/ccfzf`): `read_children` (ccfzf:1336-1380) читает `children/<id>.json` для запрошенных сессий и кладёт `head`/`headId` в строки. `heads/` не читает. Пикер получает это по ssh: `ccfzf --state` на pc-virt (`state_source.rs:90-95`).
- **Пикер:** дерево вкладывает на любую глубину, циклы рвёт. Группы раскладки - `place_order.rs` `group_ids` (:524-547): строка с родителем пропускается, группа = корень + живые прямые дети. В фикстуре `test/fixtures/head-groups.json` случай "nested" (h→x,y; x→x1) даёт только `[[h,x,y]]`, дети x не раскладываются никогда.

## Часть 1. Spawn по проекту head

### Правило (решено со Стасом)

Новые правила **добавляют проход, старый не заменяют** (мой выбор, по ревью строителя): `cwd`, который точным совпадением есть в `claudeWt.projects`, проходит как сейчас, с `headId` или без, с окном head на этой машине или без. Иначе пропали бы spawn через `--machine`/`--url` на машину без окна head.

Если `cwd` не в списке, запрос с `headId` проходит, когда:

1. `headId` - сессия, у которой есть окно в трекере окон этой машины (`windows[headId]`), то есть живой head, видимый менеджеру.
2. Каталог head (`headCwd` в теле запроса) есть в `claudeWt.projects` точным совпадением **или лежит внутри `childCwdRoot`** (мой выбор). Иначе внук, чей head открыт в amnezia-shared-panel, получил бы 403, а Стас разрешил иерархию. Пустить head из-под корня не шире, чем пустить туда ребёнка.
3. `cwd` ребёнка - абсолютный POSIX-путь внутри `childCwdRoot`, после нормализации: без `..`, `.`, двойных `/`, без хвостового `/`. Сам корень ребёнку не годится, нужен подкаталог. Символы-ловушки (`UNSAFE`) - 400, как сейчас.

Запрос без `headId` (ручной запуск, project hotkey) с `cwd` вне списка - 403, как сейчас.

Отказы: нет окна head или `headCwd` ни в списке, ни под корнем - 403 с причиной; `cwd` вне корня - 403; кривой путь - 400.

Менеджер на Windows сравнивает строки и симлинки не видит. Симлинк под `~/projects`, ведущий в `~/.ssh`, прошёл бы. Поэтому корень повторно проверяет обёртка `claude-wt-new` на pc-virt по уже разрешённому пути (`pwd -P`, строка 68): вне корня - отказ. Корень обёртка получает от менеджера (аргумент или переменная окружения в команде запуска, решает строитель). Нет корня - проверка не делается, как сейчас (мой выбор).

Подделать запрос сможет только тот, кто знает живой sessionId head на этой машине. Стас принял это ("ок" на playback).

### Конфиг

```yaml
claudeWt:
  childCwdRoot: /home/popstas/projects   # корень каталогов детей; нет ключа - ребёнок только из claudeWt.projects, как сейчас
```

Имя ключа - мой выбор. Одна строка, не список: Стас назвал один корень.

### Запуск ребёнка вне списка

Профиль терминала и остальные настройки запуска (то, что сейчас `profileForTerminal` и соседи берут по `cwd`) ребёнок берёт так: свой `cwd` в `claudeWt.projects` - от своего, как сейчас; иначе от `profileCwd` из запроса, если он в списке; иначе глобальный `cfg.profile`, как `profileForTerminal` делает для чужого каталога уже сейчас.

### spawn.mjs

Шлёт:
- `headCwd` - каталог head из `~/.claude/sessions/$CLAUDE_PID.json` (`cwd`) или из метки head;
- `profileCwd` - ближайший по цепочке `headId` (сам head, его родитель и т.д. по `~/.ccfzf/children`) каталог, который есть в `projects` трекера окон выбранной машины (`~/.ccfzf/windows/<host>.json`, поле `projects`). Не нашёлся - поле не слать. Так внук из amnezia-shared-panel получает профиль ExpertizeMe (мой выбор: Стас сказал "по родительскому проекту"). Текст `why` на 403 обновить: причина от менеджера, а не только "cwd is not in claudeWt.projects". SKILL.md: строка про 403.

## Часть 2. Иерархия и привязка

### Снять одноуровневое правило

- `head-mark.mjs`: ребёнок может стать head. Отказ убрать; в выводе показать родителя (`parent: {head, headId}`), если запись ребёнка есть.
- `head-session/SKILL.md:12`: убрать "проект не начинать". Решение Стаса 12.11 заменяет прежнее.
- `spawn.mjs:52-53`, `close.mjs:44`: убрать отказ "вызывающий - ребёнок".
- Обёртка `~/projects/shell/ccfzf/claude-wt-new:118` ("is itself a child session ... and cannot open children"): убрать отказ. Без этого окно внука откроется и встанет на exit 3. Задача исполнителю ccfzf, со своим релизом.
- Глубина не ограничена.

### Привязка

Новый скрипт рядом с head-mark, например `head-session/head-adopt.mjs <имя|sessionId>...` (имя - мой выбор). Для каждой цели:

1. Найти сессию: по sessionId или имени через `claude agents --json` / `~/.claude/sessions/*.json`, как это делает spawn.mjs для свободности имени. Не нашёл или имя неоднозначно - отказ по этой цели, остальные дальше.
2. Отказы: цель - сам head; цель - предок head (идти по `headId` вверх от head; цикл). Цель не живая - отказ.
3. Записать `~/.ccfzf/children/<sid>.json` тем же форматом, что spawn, плюс:
   - `adopted: true` (spawn пишет без поля или `false`);
   - если запись уже была с другим `headId` - `prevHeadId`, `prevHead` (перепривязка, Стас);
   - `createdAt` - время привязки.
   Атомарно, через временный файл, как head-mark.
4. Уже ребёнок этого head - ничего не менять, `already: true`.
5. Вывод JSON по каждой цели: sessionId, name, cwd, adopted/already/refused, why.

Когда вызывает head-session: на старте после head-mark и ListAgents - для каждого названного исполнителя; позже - когда пользователь добавляет исполнителя в разговоре. Строка в SKILL.md (раздел "Старт").

Снятие привязки: `head-adopt.mjs --release <имя|sessionId>` удаляет запись, если `headId` = я. Окно не трогает. Нужна, когда исполнителя убрали из проекта. Отдельного решения Стаса нет, мой выбор; можно отложить.

Прежний head перепривязанной сессии ничего не получает: она просто пропадает из его детей. Сообщение ему - нет, мой выбор.

### session-close

Закрывает привязанных так же, как спавненных: проверка `child.headId === me` уже работает после записи. Правило "только после явного да Стаса на конкретную сессию" и busy-отказ без `--force` прежние. В выводе `adopted`, чтобы в отчёте было видно, что сессию head не создавал. Удаление `<id>.task.md` у привязанного - не применимо (его нет), не падать.

### Пикер: группы с иерархией

`place_order.rs` `group_ids`:

- Группа есть у каждой сессии, у которой есть живые прямые дети: `[head, дети...]`. Сессия посередине входит в две группы: ребёнком в группу родителя и head-ом в свою.
- Порядок групп и выбор по выбранной сессии (сейчас "первая подходящая группа", дизайн 11.11):
  1. выбранная - head с живыми детьми → её собственная группа (Стас: "её собственную с её детьми");
  2. иначе выбранная - ребёнок → группа её родителя;
  3. ничего не выбрано → как сейчас (группа с активным окном у менеджера).
- Цикл в данных (не должен возникать после проверки в head-adopt, но записи правят руками) - рвать как дерево: узел становится корнем.
- Фикстура "nested": ожидание поменять на `[[h,x,y],[x,x1]]`, добавить случаи "выбран x → [x,x1]", "выбран x1 → [x,x1]", "выбран y → [h,x,y]".

Менеджер правок не требует, если пикер шлёт в `groups` ровно одну нужную группу или кладёт нужную первой: менеджер берёт первую группу, в которой есть `selected`. Сессия посередине есть в обеих - поэтому порядок в `groups` значим; проще слать одну. Решает строитель пикера, контракт `claude-place` не менять.

### Агрегатор ccfzf

Ничего не нужно: `read_children` уже отдаёт `head`/`headId` для любой сессии. Проверить, что привязанные сессии (их окна открывались не через session-new) тоже попадают в список сессий, для которых он читает записи.

### Менеджер: реестр детей

`child-registry.js` про привязанных не знает: их окна открывались не через `session-new`. Это влияет только на подсчёт мест в зоне при следующем spawn (`child-place.js:127`): привязанное окно, стоящее в зоне стопки, не учтётся и следующий ребёнок может лечь на его место. До хоткея это допустимо (решение 11.11 "окна стоят до хоткея"), Ctrl+Win+F10 раскладывает всех. Правку оставляю строителю менеджера на усмотрение: учитывать занятость зоны по трекеру окон, а не только по реестру.

## Часть 3. Режим "колода" и описания в настройках

Добавлено 12.11 по просьбе Стаса: "не хватает третьего режима: head-children, когда зона не делится по вертикали, а все дети размещаются в одну и ту же позицию друг под другом". Ещё Стас попросил описания поведения в настройках, желательно с мини-схемами.

### Режим

Третье значение `claudeWt.childPlacement`: `deck`. Стас назвал режим head-children, имя значения - мой выбор, `deck`: stack и free тоже про head и детей. Стас может переименовать при чтении.

- **Открытие ребёнка:** ребёнок занимает вторую основную зону монитора head целиком (та же зона, что выбирает stack: `pickStackZone`). Зона не делится, братья не ужимаются и не двигаются. Новый окажется сверху.
- **Ctrl+Win+F10** (Стас: "и при открытии новых детей, и в раскладке"): при `childPlacement: deck` group-раскладка кладёт head в первую зону пары, а всех детей - во вторую целиком, одним прямоугольником. При `stack` и `free` раскладка прежняя (до трёх мест, дальше поверх).
- Порядок по глубине после раскладки (мой выбор): выбранная сессия сверху, если она ребёнок; иначе порядок не трогать.
- Head не в основной зоне и прочие правила 11.11 - как у stack.
- Правило "до трёх мест, дальше 1-2-3 поверх" в deck не действует: мест одно.
- Поле `slot` в трекере у детей deck - `1`.

Раскладке нужно знать режим: менеджер читает свой `claudeWt.childPlacement`, контракт `claude-place` не меняется.

### Описания в настройках

Вкладка Claude в трее, селект `claudeWt.childPlacement`: под селектом описание выбранного режима и мини-схема. Схема - статичная картинка (SVG или моноширинный блок, решает строитель), показывает монитор с двумя зонами: H - head, c1, c2, c3 - дети.

```
stack           free               deck
┌────┬────┐     ┌────┬────┐        ┌────┬────┐
│ H  │ c1 │     │ H  │ c1 │        │ H  │ c3 │
│    ├────┤     │    │    │        │    │(c2)│
│    │ c2 │     └────┴────┘        │    │(c1)│
│    ├────┤     c2, c3 - в свобод- └────┴────┘
│    │ c3 │     ные зоны других    все во второй
└────┴────┘     мониторов          зоне, друг на друге
```

Тексты (русские, мой выбор - вкладка сейчас на английском, Стас может вернуть):
- **stack** - ребёнок во второй зоне монитора head; зона делится по вертикали, до трёх мест, четвёртый ложится поверх первого.
- **free** - ребёнок в свободную основную зону любого монитора; свободных нет - делит зону со своими, затем поверх.
- **deck** - все дети во второй зоне целиком, друг на друге; видно верхнего, остальные через пикер.

Строкой ниже: "Ctrl+Win+F10 раскладывает группу по этому же режиму".
