# Конфиг переезжает на YAML

2026-08-17

## Зачем

Три цели, названные заказчиком, в порядке важности:

1. **Единообразие связки.** У ccfzf-picker конфиг — `config.yaml`, у менеджера —
   исполняемый JS. Одну связку приходится править в двух синтаксисах.
2. **Правка программами.** Конфиг правят не только руки: скилл `project-add`
   дописывает `claudeWt.projects`. Сейчас он редактирует JS текстовыми заменами —
   приём, который ломается на первой же непредусмотренной форме записи.
3. **Данные вместо кода.** `require` тянет за собой кэш модулей, `structuredClone`
   и откат на «неклонируемый конфиг» — всё это существует только потому, что в
   конфиге может оказаться функция.

Не цель: читать конфиг из чего-то, кроме Node. Rust-трей свои настройки держит
в `tauri-plugin-store` и в этот файл не заглядывает; менять это не требуется.

## Решение в одну строку

`claudeWt.config.js` → `windows11-manager.config.yaml`, разбирается пакетом
`yaml` v2, JS-дорога вырезается целиком, а живой конфиг переносится руками под
контролем команды, доказывающей эквивалентность.

## Что известно про живой конфиг

Замерено на popstas-pc 2026-08-17 (`config.cjs`, 683 строки, в git не хранится —
отслеживается только `config.example.cjs`):

- 14 именованных констант вида `const homeMon1RightHalf = {...}`;
- десятки правил, собранных спредом с переопределением:
  `{...homeMon1RightHalf, ...{ titleMatch: 'Telegram' }}`;
- константы, собранные из других констант (`const homeMon1RightThird = {
  ...mon1RightThird, ...{...} }`);
- закомментированные правила, которые живут как история решений;
- никаких вычислений, `require`, шаблонных строк и функций.

Отсюда два следствия, определившие дизайн. Первое: YAML это выражает —
якорями (`&name` / `*name`) и merge-ключами (`<<:`). Второе: **автоматический
конвертер их не сохранит** — к моменту, когда JS вычислен, спредов уже нет, и
дамп даст плоский файл с геометрией, размноженной по правилам.

## Загрузчик

`src/config.js` переписывается вокруг `parse()` из пакета `yaml` v2.

**Пути.** `resolveConfigPath()` перебирает те же пять мест, что и сейчас, меняя
расширение на `.yaml`:

```
%APPDATA%/windows-mqtt/windows11-manager.config.yaml
%APPDATA%/windows11-manager/config.yaml
~/.config/windows11-manager.config.yaml
./windows11-manager.config.yaml
<repo>/config.yaml
```

Только `.yaml`, без второго имени `.yml`: у пикера файл называется `config.yaml`,
а единообразие связки — первая из целей. Два допустимых имени в каждом из пяти
мест дали бы десять кандидатов и вопрос «а почему он читает не тот файл».

**Разбор.** `parse(text, { merge: true })`. Опция обязательна: без неё `yaml` v2
разбирает `<<` как обычный ключ со строковым именем, молча — правило получит поле
`<<` и ни одного унаследованного значения.

**Что остаётся от старого кода.** Кэш по mtime — тик демона claude-wt зовёт
`getConfig()` раз в секунду, и без кэша это 234 МБ RSS против 49 МБ (замерено,
см. комментарий в текущем `config.js`). `structuredClone` на выдаче — вызывающие
пишут прямо в объекты конфига (`placement.js` ставит `rule.pos`, `findWindows()`
дописывает `titleMatch`), и общий объект копил бы эти пометки между вызовами.
Поле `_configPath` остаётся: по нему ориентируются диагностические команды.

**Что уходит.** Флаг `cloneable` с откатом на пересборку через `require`: он
заведён ради функций в конфиге, а в YAML их не бывает. Вместе с ним уходит
`createRequire` и работа с `require.cache`.

**Отказы.** Сейчас отсутствующий файл роняет `require` стеком, а испорченный —
синтаксической ошибкой JS. Становится:

- файла нет ни в одном из пяти мест — ошибка, перечисляющая все просмотренные
  пути;
- YAML не разбирается — сообщение с номером строки и колонки (пакет `yaml` даёт
  их в `YAMLParseError.linePos`), без стека.

## Якоря

Константы переезжают в верхний ключ `x-anchors` (соглашение docker-compose для
служебных ключей), который загрузчик **удаляет** сразу после разбора:

```yaml
x-anchors:
  homeMon1RightHalf: &homeMon1RightHalf
    desktop: 1
    fancyZones: { monitor: 1, position: 3 }

windows:
  - <<: *homeMon1RightHalf
    titleMatch: Telegram
```

Удаление не косметика: без него ключ попадёт в сравнение со старым конфигом, и
проверка эквивалентности будет сообщать о расхождении, которого нет.

Альтернатива — объявлять якорь прямо на первом использовании — отвергнута:
первое правило становится определением для остальных, и его нельзя удалить или
переставить, не сломав соседей молча.

Закомментированные правила переезжают обычными `#`-комментариями.

## Миграция

Проверка эквивалентности **не читает старый JS**. Иначе `require` пришлось бы
оставить в новой версии ровно затем, ради чего его выпиливают. Снимок делает
старая версия, на машине, без всякой поддержки со стороны кода:

```
node -e "console.log(JSON.stringify(require('C:/Users/popstas/AppData/Roaming/windows-mqtt/windows11-manager.config.js')))" > old.json
```

Две новые команды CLI:

- `node src config-dump [путь] [--json]` — печатает разобранный конфиг: по
  умолчанию YAML, при `--json` — JSON. Без аргумента берёт тот файл, который
  выбрал бы сам менеджер (`resolveConfigPath()`), с аргументом — названный.
  Черновик для миграции и отладка «что менеджер на самом деле прочитал».
- `node src config-verify <a> <b>` — грузит два файла (`.json` или `.yaml`),
  сравнивает глубоким равенством и печатает расхождения путями:

```
разошлись: windows[12].fancyZones.position  3 ≠ 1
разошлись: claudeWt.projects[4].profile  "Work" ≠ отсутствует
2 расхождения
```

Совпало — печатает «конфиги эквивалентны» и выходит с нулём; разошлось — код
выхода 1, чтобы это годилось для скрипта.

Сравнение идёт по разобранным структурам, а не по тексту: порядок ключей,
отступы и комментарии на поведение менеджера не влияют и расхождением не
считаются.

  переносятся дословно — они и есть документация формата.

- Скилл `project-add` (`~/.claude/skills/project-add/`): переучить на Document

  а это ровно та цель, ради которой затевался переезд.

## Порядок выкатки

Дороги назад у выкатки нет: новая версия старый конфиг не прочитает вовсе.

1. На popstas-pc снять `old.json` командой выше — **до** выкатки, пока работает
   старая версия.
2. Написать `windows11-manager.config.yaml` руками, с якорями, и положить рядом
   со старым. Старая версия его не видит: она ищет только `.js`, менеджер
   продолжает работать.
3. На своей машине: `node src config-verify old.json config.yaml` — зелёный.
4. Только теперь деплой. Трей перезапускается и читает YAML.
5. Откат, если что-то не так: `.js` лежит на месте, выкатить прежний тег.

## Тесты

Юнит-тесты (vitest, как весь проект):

- якоря и merge-ключи разбираются: правило получает унаследованные поля, а свои
  перебивают унаследованные;
- `x-anchors` в выдаче отсутствует;
- кэш: два вызова подряд без смены mtime читают файл один раз; смена mtime —
  перечитывает; `reloadConfigs()` перечитывает независимо от mtime;
- выдача — своя копия: правка результата не видна следующему вызову;
- файла нет — ошибка перечисляет просмотренные пути;
- битый YAML — сообщение содержит номер строки;
- `config-verify`: расхождение в глубине объекта, расхождение внутри массива,
  ключ есть у одного и отсутствует у другого, полное совпадение.

Тесты, мокающие `getConfig()`, не трогаются: подпись функции не меняется.

## Зависимости

Добавляется `yaml` (v2, eemeli). Сейчас у проекта две зависимости — `commander`
и `mqtt`. `js-yaml` в дереве есть транзитивно (через eslint), но не годится:
комментарии при round-trip он не сохраняет, а без этого правка конфига
программой уничтожает документацию формата.
