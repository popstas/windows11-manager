# claude-wt: снапшоты сессий

Дизайн от 2026-08-01. Развивает `2026-07-31-claude-wt-design.md`.

## Проблема

`claude-wt restore` не восстанавливает сессии. Причина воспроизведена и измерена 2026-08-01.

**1. `lastLayout` обнуляется быстрее, чем им успевают воспользоваться.** Демон тикает раз в секунду и переписывает `lastLayout` тем, что видит на экране. Замер: три сессии в `lastLayout`, `Stop-Process WindowsTerminal`, через **1.5 секунды** `lastLayout: []`. Запущенный следом `claude-wt restore` печатает `nothing to restore`.

`detectCrash()` спасает только один сценарий — машина ушла в ребут вместе с демоном, файл остался с прошлой записью. Всё остальное (закрыл окна руками, упал WT, случайно закрыл сессию) даёт пустой `lastLayout` через секунду.

**2. Координаты в `slots` дрейфуют.** `slots[id].bounds` — это «где окно этой сессии сейчас», а не «где оно было в рабочем раскладе». Замер: слот `3ea51f99` держал `{734,0,809×1381}`; после закрытия и восстановления сессии в слоте оказалось `{776,16,992×864}` — дефолтная геометрия Windows Terminal. Восстановление из слотов вернуло окно не на место.

**3. Сессия, чей заголовок не резолвится, не отслеживается вовсе.** Замер: на экране три окна, в `lastLayout` два. Третье, `rich-telegram`, не нашлось в дампе ccfzf (93 сессии) — сессию переименовали, дамп остался со старым заголовком. Слота нет → в списке нет → restore теряет её молча.

Дополнительно: заголовок `obsidian-agent-base` носили **7** сессий дампа. `indexSessions()` выбирает live-first, поэтому слот мог указывать на вчерашний транскрипт, а restore — открыть не то окно.

## Что чинится

Расклад запоминается **снапшотами** — замороженными копиями состава и координат, которые не переписываются каждую секунду. `restore` начинает читать снапшот, а не `lastLayout`.

В репозитории нет файлов, которые есть в опубликованной 2.0.0 (`node_modules/windows11-manager` у windows-mqtt) и которых нет **ни в одном коммите** (`git log --all` пуст). Похоже, версию опубликовали из рабочего дерева с незакоммиченными файлами.

Восстановить из установленной копии:

Это прямая зависимость: `monitorNumberForBounds()` нужен снапшотам, `claudeWtSessions()` — точка входа для F5.

Заодно закрывается пункт TODO «мониторы не отслеживаются»: `monitor` не хранится в слотах, а считается из `bounds` по центру окна — и это правильно, монитор производен от координат.

## Модель данных

Отдельный файл рядом со `statePath`, по умолчанию `claude-wt-snapshots.json`. Отдельный — чтобы `claude-wt clear` не сносил историю вместе с рабочим состоянием и чтобы снапшоты не утяжеляли файл, который демон переписывает на каждое изменение раскладки.

```jsonc
{
  "version": 1,
  "snapshots": [                      // новые первыми
    {
      "id": "2026-08-01T16-12-33",    // время создания, оно же человекочитаемый id
      "created": 1785531153,          // unix seconds
      "updated": 1785532001,          // последнее обновление координат
      "sessions": [
        {
          "id": "3ea51f99-7937-4db9-a530-6f982982c63c",
          "title": "obsidian-agent-workspace",
          "cwd": "/home/popstas/projects/text/obsidian-agent-base",
          "bounds": { "x": 734, "y": 0, "width": 809, "height": 1381 },
          "desktop": 1,
          "monitor": 2
        }
      ]
    }
  ]
}
```

`sessions[]` — **копия** данных слота, а не ссылка. Иначе старый снимок показывал бы сегодняшние координаты, и «посмотреть список окон за разные снимки» теряет смысл; ровно на этом сегодня погорел restore.

`monitor` считается в момент записи через `monitorNumberForBounds(getMons(), bounds)`. В снимке он должен остаться таким, каким был тогда, даже если мониторы потом переключили.

Запись — атомарная, тем же способом, что и `state.js`: временный файл, `fsync`, `rename`.

## Жизненный цикл

В тике демона считается `compositionKey` — отсортированные id сессий, у которых **сейчас** открыто окно.

**Состав изменился.** Взводится debounce на `snapshots.debounceMs`. Изменился снова до срабатывания — таймер перезапускается. Дожил без изменений → пишется **новый** снапшот. Снимок фиксирует не момент изменения, а устоявшееся состояние: пока пользователь открывает три сессии подряд, промежуточные конфигурации в историю не попадают.

**Состав тот же, съехали координаты.** Обновляется **последний** снапшот на месте: `updated`, `bounds`, `desktop`, `monitor`. Новой записи в списке не появляется — таскание окна мышкой не должно плодить строчки в меню.

**Пустой состав не снимается.** Закрыл всё на ночь — снапшот с нулём сессий не пишется. Иначе `snapshots-restore last` наутро означал бы «восстановить ничего»; вместо этого последним остаётся рабочий набор.

**Вытеснение.** Хранится `snapshots.keep` снимков, лишние отбрасываются с хвоста.

**Запись на диск** — только когда содержимое реально изменилось, по отдельному fingerprint (как `layoutFingerprint()` для state), чтобы не класть запись на каждый тик.

Debounce-таймер живёт в памяти демона. Если демон убили внутри окна ожидания, изменение состава в историю не попадёт. Принято сознательно: N минут стабильности означают «это была не случайная конфигурация», а убитый демон и так ничего не гарантирует.

## Обновление дампа ccfzf

Дамп (`sessionsFile`, у popstas — `V:/.ccfzf.sessions.json`) генерируется на удалённой машине. Пока он несвежий, переименованная сессия не резолвится и выпадает из отслеживания.

Два триггера, оба через одну функцию с общим debounce:

**F5 в окне выбора сессий.** windows-mqtt зовёт `claudeWtSessions({ refresh: true })`. Кэш возвращается немедленно, ssh уходит в фон. Обычные тики фида (`startSessionsFeed()` дёргает `claudeWtSessions()` раз в секунду, пока открыт picker) флага не передают — иначе получился бы спавн ssh-процесса каждую секунду, ровно тот класс паразитной нагрузки, за который в проекте уже заплачено дважды (`VirtualDesktop11.exe` в цикле; `loudness`, спавнивший exe на каждый опрос громкости).

**Заголовок терминала не резолвится.** Демон уже вычисляет `unresolvedTitles(nextWindows)` для диагностики. Как только там появляется новый устоявшийся заголовок, взводится debounce на `sessionsRefresh.debounceMs` (60 с) и дамп обновляется. Триггер именно на **нерезолвящийся** заголовок, а не на любое переименование: когда всё и так сходится, ssh дёргать незачем.

Ограничители: пока один refresh в полёте, второй не стартует; ssh запускается с `timeoutMs` и никогда не блокирует возврат кэша.

Досылать результат не нужно — `loadSessionIndex()` перечитывает дамп по mtime, и ближайший тик фида отдаёт свежий список.

## Команды

```
claude-wt snapshots-list [--json]
claude-wt snapshots-restore <id|last> [--session <id...>]
```

`snapshots-list` без флага печатает человекочитаемую таблицу, с `--json` — структуру для машинного разбора.

`last` означает **буквально самый свежий снимок**. Никакого поиска «последнего, где есть потерянное»: команда, молча уходящая на три снимка назад, оставляет пользователя гадать, откуда взялось окно.

`claude-wt restore` становится алиасом `snapshots-restore last`. Это и есть корневая починка: `lastLayout` обнуляется через секунду, снапшот — нет.

Судьба флагов существующей команды: `--session <id...>` сохраняется (поднять из снимка только перечисленные сессии), `--force` удаляется — дедупликация теперь безусловна, и включать её флагом больше нечего.

Библиотечное API для windows-mqtt:

```js
claudeWtSnapshots()                        // { ok, snapshots: [...] }
restoreSnapshot({ id, sessionIds })        // { restored: [], skipped: [] }
```

```
Claude Sessions

│   ├─ obsidian-agent-workspace   (desktop 1 · monitor 2)
│   ├─ home                       (desktop 1 · monitor 1)

└─ …
```

Последние 5 снимков, в заголовке время и количество сессий. Клик по сессии поднимает только её, из координат **этого** снимка. «Восстановить всё» — весь снимок.

## Восстановление

- Координаты берутся **из снапшота**, не из текущих `slots`.
- Дедупликация по session id против `openSessionIds()` — **всегда**. В снимке 3 сессии, две открыты → поднимается одна. Отказа «сначала закройте их» больше нет: нынешнее поведение `restore` без `--force` — отказаться целиком, если хоть одна сессия на экране — и есть то, что делает команду бесполезной в самом частом случае («случайно закрыл одну из трёх»).
- Все сессии уже открыты → «нечего восстанавливать», выход 0.
- Запуск последовательный: `restore.launchDelayMs` между окнами, ожидание нового окна, `restore.settleMs`, затем `placeWindowByConfig`. Механика сохраняется без изменений — она рабочая, проверено сегодня: три сессии поднялись и встали по координатам с точностью до пикселя.

Замечание из практики: после `claude --resume` окно может какое-то время висеть с заголовком профиля (`popstas`) — Claude Code не перерисовывает экран, пока в него не нажмут (стрелка вниз). На восстановление это не влияет (процесс на удалённой машине запущен), но до перерисовки окно не привязывается к сессии и не попадает в снимок.

## Состояние агента в списке сессий

Реализовано 2026-08-01, до снапшотов. Отвечает на вопрос «что происходит в этом
окне», которого в списке не было вовсе.

**Читать состояние из Windows нельзя.** Хук `wt-progress.sh` выставляет
прогресс-бар последовательностью OSC 9;4, Windows Terminal превращает её в
вызов `ITaskbarList3::SetProgressState`. У этого интерфейса нет геттеров, а
состояние живёт внутри explorer.exe — ни в свойствах окна, ни в его стилях его
нет. Единственный теоретический путь, UI Automation по кнопке таскбара,
ненадёжен сам по себе и вдвойне под ExplorerPatcher. Поэтому источник — файл,
который пишет тот же хук, что и рисует бар.

**Кто что пишет** (на стороне агента, `/home/popstas` = `V:`):

- `wt-progress.sh` → `~/.claude/claude-wt/<id>.state.json`: `state`, `event`,
  `message`, `transcript`, `cwd`, `updated`. Состояния: `active` (start,
  tool-start, tool-done), `question` (attention с реальным вопросом), `review`
  (stop, fail), `idle` (attention «waiting for your input»).
- `claude-wt-agent-state.sh` → `<id>.meta.json` на `SessionStart`: `cwd`,
  `transcript`, `source`, `host`, `started`. Закрывает ту же дыру, что и
  обновление дампа: новая или переименованная сессия становится известна сразу.

По файлу на сессию, запись атомарная (временный файл + `mv`): хуки параллельных
сессий не дерутся за общий файл. Файлы старше 7 дней подчищаются на `start`.

**Кто читает.** `progress.js` — с кэшем по mtime, только для сессий, у которых
есть слот, и **только из view-слоя**. В тике демона ему не место: каталог лежит
на сетевом диске, а тик ходит раз в секунду.

`buildSessionList()` добавляет `agentState`, `agentEvent`, `agentMessage` и
`lastActivity` (максимум из отметки хука и `lastSeen` слота — хук точнее, но
может быть не установлен).

**Как показывается.** Пикер windows-mqtt: зелёный — работает, жёлтый —
спрашивает, оранжевый — закончил и результат не смотрели, серый — простаивает,
у закрытой сессии кружка нет (место под него остаётся, иначе строки съезжают).
Живая сессия без состояния — серая, а не зелёная: зелёный означает «работает
прямо сейчас», а у сессии, поднятой до установки хука, состояния нет вовсе.
Справа возраст последней активности (`now`, `5m`, `2h`, `3d`), при наведении —
полный `cwd` и текст уведомления: `message` единственное, что отличает «нужно
разрешение» от «просто жду ввода», оба приходят одним событием `attention`.

Обновление: фид пикера зовёт `claudeWtSessions()` раз в секунду, пока окно
открыто, а чтение кэшировано по mtime — запись хука видна максимум через
секунду без лишнего ввода-вывода. В фоне статусы не опрашиваются: каждый тик
сканирует окна, и делать это ради невидимого списка незачем.

## Конфиг

```js
claudeWt: {
  // ...существующее
  progressDir: '',       // у popstas: 'V:/.claude/claude-wt'
  snapshots: {
    enabled: true,
    path: '',            // пусто → claude-wt-snapshots.json рядом со statePath
    debounceMs: 60000,   // у popstas: 300000
    keep: 20,            // у popstas: 5
  },
  sessionsRefresh: {
    enabled: false,      // без команды обновления фича выключена
    command: 'ssh',
    args: [],            // например: ['popstas@pc-virt.popstas.pro', '<команда генерации дампа>']
    debounceMs: 60000,
    timeoutMs: 10000,
  },
}
```

`sessionsRefresh.args` заполняется в личном конфиге: точная команда генерации дампа на pc-virt известна только пользователю. В репозитории список пуст и `enabled: false`, так что по умолчанию ssh не запускается никогда.

## Раскладка по файлам

- `src/claude-wt/snapshot-helpers.js` — чистая логика, без I/O: `compositionKey()`, `shouldSnapshot()` (debounce), `appendSnapshot()`, `updateLastSnapshot()`, `pruneSnapshots()`, `snapshotFingerprint()`, `planSnapshotRestore()`, дедупликация против открытых.
- `src/claude-wt/snapshots.js` — чтение/атомарная запись файла, реэкспорт хелперов. По образцу `state.js`.
- `src/claude-wt/refresh.js` — запуск команды обновления дампа: debounce, guard «один в полёте», таймаут.
- `src/claude-wt/index.js` — вызов снапшотера из тика, триггер refresh по нерезолвящемуся заголовку.
- `src/claude-wt/restore.js` — `restoreSnapshot()`, `restore` как алиас `snapshots-restore last`.
- `src/claude-wt/view.js` — параметр `{ refresh }` у `claudeWtSessions()`.
- `src/index.js` — команды `snapshots-list`, `snapshots-restore`.

Логика — в `*-helpers.js`, I/O — в модулях-обёртках. Так заведено в проекте: тесты импортируют хелперы и не тянут node-window-manager.

## Тестирование

Юнит-тесты (vitest, без I/O) на `snapshot-helpers.js`:

- `compositionKey()` не зависит от порядка окон;
- новый снимок пишется только после `debounceMs` стабильности; изменение внутри окна ожидания перезапускает таймер;
- смена только координат обновляет последний снимок, не создаёт новый;
- пустой состав не пишется;
- `pruneSnapshots()` держит `keep` штук, отбрасывает старые;
- `planSnapshotRestore()` исключает уже открытые сессии: 3 в снимке, 2 открыты → план из одной;
- координаты в плане берутся из снимка, даже когда `slots` содержит другие.

Плюс `refresh.js`: второй вызов внутри debounce не запускает процесс; вызов при активном refresh игнорируется.

Ручная проверка (прогонялась сегодня, воспроизводима):

1. `node src/index.js claude-wt snapshots-list` — снимок с текущими сессиями на месте.
2. `Get-Process WindowsTerminal | Stop-Process -Force`.
3. `node src/index.js claude-wt snapshots-restore last` — окна возвращаются на свои координаты.
4. Закрыть одну сессию из трёх, повторить — поднимается только недостающая.

## Вне рамок

- Дубли заголовков в дампе (7 сессий с именем `obsidian-agent-base`) — снапшоты хранят id и от разрешения по заголовку не зависят, но привязка *живого окна* к сессии по-прежнему может выбрать не ту. Отдельная задача.
- Перерисовка окна после `claude --resume` — поведение Claude Code, не этого проекта.
