# claude-wt — позиционная память для окон Claude Code

Статус: дизайн утверждён, к реализации не приступали
Дата: 2026-07-31

## Проблема

Сессии Claude Code живут в окнах Windows Terminal, каждая в своём окне. Заголовок
окна отражает текущую сессию: пока claude запущен, WT показывает её название,
после выхода — приглашение шелла (`popstas@pc-virt: ~/...`). Одно и то же окно за
день проходит через несколько сессий.

Позиция окна при этом ни к чему не привязана. Вернувшись в сессию, над которой
работал утром, получаешь её в произвольном месте экрана, и раскладку приходится
собирать руками заново. После аварийной перезагрузки теряется вся раскладка
целиком.

claude-wt запоминает, где живёт каждая сессия, и возвращает окно на это место,
когда сессия в нём открывается снова.

## Скоуп v1

Входит:

- фоновое наблюдение за окнами Windows Terminal и их заголовками;
- запоминание последней позиции для каждой сессии Claude Code;
- возврат окна на сохранённое место при входе в известную сессию;
- восстановление раскладки после аварийной перезагрузки (перезапуск сессий и
  расстановка окон), по ручной команде.

Не входит:

- вкладки WT и несколько сессий в одном окне — модель «одна сессия = одно окно»;
- FancyZones-зоны как способ хранения позиции;
- локальные Windows-сессии claude — всё идёт по ssh на pc-virt;
- закрепление окон (pin), UI редактирования позиций, синхронизация раскладок
  между машинами.

## Что уже есть

Модуль встраивается в windows11-manager и опирается на готовое:

- `src/windows.js` — `getWindows()` с фильтрацией системных окон; у окна доступны
  `id`, `title`, `path`, `processId`, `getBounds()`, `setBounds()`;
- `src/placement.js` — `placeWindowByConfig(rule)` применяет bounds, корректирует
  их при смене scale-фактора монитора, повторяет попытку при несовпадении и
  переносит окно на виртуальный стол. claude-wt не вызывает `setBounds` напрямую,
  а формирует правило и отдаёт его сюда;
- `src/placement.js:272` — автоплейсер на `setInterval` с тумблером в трее Tauri:
  готовый образец фонового демона;
- `src/geometry.js` — примитивы для работы с прямоугольниками и мониторами;
- конвенция «I/O-модуль + чистый `*-helpers.js` + vitest».

Признак свёрнутого окна в проекте — `getBounds().x < -10000`.

Источник данных о сессиях — дамп ccfzf (`~/.ccfzf.sessions.json` на стороне
Linux, виден с Windows как `V:\.ccfzf.sessions.json`). Это 200 новейших сессий по
всем проектам (`DUMP_SESSIONS = 200`); поле верхнего уровня `project` относится к
последнему просмотренному проекту и для нас не значимо. У каждой сессии есть
`id`, `cwd`, `title`, `mtime`, `live`, `frozen`. Дамп переписывается при каждом
запуске ccfzf, а новые сессии запускаются только через него.

## Архитектура

Пять модулей под `src/claude-wt/`, разделённые по признаку «трогает ли I/O»:

| Модуль | Ответственность | I/O |
|---|---|---|
| `sessions.js` | Читает дамп ccfzf, строит индекс `title → сессия`. Перечитывает файл только при изменении mtime | Чтение файла |
| `state.js` | Чтение и запись файла состояния, атомарно (tmp + rename) | Чтение и запись файла |
| `tracker.js` | Ядро: из предыдущего и текущего снимка окон выводит новое состояние и список действий | Нет |
| `index.js` | Демон: таймер, `getWindows()`, вызов трекера, исполнение действий через `placeWindowByConfig` | Всё остальное |
| `restore.js` | Детект аварии, план перезапуска, последовательный запуск и расстановка | Запуск процессов |

Чистые функции (`indexSessions`, `step`, `detectCrash`, `planRestore`,
`clampBoundsToMonitors`) выносятся в `*-helpers.js` и покрываются тестами без
Windows, как это уже сделано для placement, windows, store и остальных.

Точка входа в CLI — команда `claude-wt` в `src/index.js` с подкомандами `watch`,
`status`, `restore`, `clear`. В трее Tauri — тумблер «claude-wt» рядом с
автоплейсером и пункт «Restore claude sessions».

Атомарная запись состояния обязательна: демон пишет файл раз в секунду, и
оборванная запись в момент отключения питания не должна оставлять мусор — именно
этот файл нужен для восстановления после той самой перезагрузки.

## Модель данных

Состояние ключуется по **id сессии**, а не по заголовку. Заголовок не стабилен:
ai-title обновляется по ходу разговора, и позиция, привязанная к строке,
потерялась бы при первом переименовании. Заголовок — это индекс поиска, причём с
историей.

```jsonc
{
  "version": 1,
  "slots": {
    "dad9f8b1-df6c-4bd9-91f2-5e4e3b822075": {
      "titles": ["ccfzf", "ccfzf — выбор сессии"],  // все виденные, новейший первым
      "cwd": "/home/popstas/projects/shell/ccfzf",
      "bounds": { "x": 100, "y": 50, "width": 1200, "height": 900 },
      "desktop": 2,
      "lastSeen": 1785460172
    }
  },
  "lastLayout": ["dad9f8b1-...", "dc0fe280-..."],  // что было открыто одновременно
  "updated": 1785460172
}
```

`bounds` — сырые координаты и размер, `desktop` — номер виртуального стола.
FancyZones как способ хранения позиции отвергнут: в `AGENTS.md` задокументировано,
что математика FZ на high-DPI мониторах делит размеры зон на scaleFactor, а
`editor-parameters.json` протухает до полной перезагрузки. Сырые bounds — это
ровно то, что пользователь выставил мышкой, и они не зависят от состояния
PowerToys.

`lastLayout` содержит id сессий, показанных в окнах терминала на текущем тике, и
переписывается на **каждом** тике, включая тот, где окон не осталось. Это
принципиально: намеренное закрытие всех окон опустошает `lastLayout`, и именно
поэтому непустой layout после перезагрузки означает аварию. Он же — вход для
восстановления.

## Сопоставление окна с сессией

Разрешение заголовка идёт по ступеням:

1. индекс из дампа ccfzf;
2. собственная история `titles` в состоянии — страховка на случай, когда V:
   отвалился или дамп протух;
3. не разрешилось — окно не наше, не трогаем.

**Коллизии заголовков.** В дампе на 200 сессий одинаковые заголовки неизбежны
(`ccfzf`, `home`). Если заголовок разрешается больше чем в одну сессию,
выбирается та, у которой стоит `live: true` и свежее `mtime`. Если и это не
разводит — окно не двигаем, пишем в лог. То же в обратную сторону: если два окна
одновременно показывают один заголовок, не двигаем ни одно. Молча угадать здесь
хуже, чем не сделать ничего: телепортация окна не туда раздражает сильнее, чем
его неподвижность.

## Трекер

На каждом тике опрашивается `getWindows()`, остаются окна `WindowsTerminal.exe`,
результат сравнивается с предыдущим снимком по `w.id`:

| Ситуация | Действие |
|---|---|
| Окно появилось (`id` новый) | Разрешить заголовок в сессию. Есть сохранённая позиция — переместить. Нет — завести слот с текущей позицией |
| `id` тот же, заголовок не менялся | Обновить `bounds` слота: пользователь подвинул окно, это и есть запоминание последнего положения |
| `id` тот же, заголовок сменился | Тот же разбор, что для нового окна. Не разрешился в сессию (вышли из claude, заголовок стал приглашением шелла) — окно осиротело, ничего не делаем, слот уже хранит последнюю позицию |
| `id` исчез | Слот остаётся, проставляется `lastSeen` |

Свёрнутые окна (`x < -10000`) в позицию не записываются — иначе один сворот
затрёт слот мусором.

Действия выражаются как правила для `placeWindowByConfig`:
`{ window: <id>, x, y, width, height, desktop }`.

### Защита от дребезга

**Грация на стабильность заголовка.** При входе в сессию заголовок меняется не
один раз (шелл → claude → название сессии). Трекер реагирует только на заголовок,
продержавшийся не менее `stableTicks` тиков (по умолчанию 2). Это же условие
блокирует запись `bounds`: пока заголовок плавает, окно не приписывается ни к
какому слоту. Цена — окно возвращается на место примерно через две секунды после
входа в сессию, а не мгновенно.

**Guard на собственный ход.** Выдав команду на перемещение, трекер помечает окно и
не записывает его `bounds` в слот, пока фактические не совпадут с целевыми или не
истечёт таймаут. Иначе неудавшийся или скорректированный по DPI перенос
запишется как намеренный выбор пользователя и затрёт правильную позицию.

## Восстановление после краха

Отличить аварию от намеренного закрытия по признаку «окон нет» нельзя. Точный
сигнал другой:

> состояние последний раз записано **до текущей загрузки системы**
> (`state.updated < boot time`, вычисляется из `os.uptime()`), а `lastLayout` в
> нём непустой.

При штатном закрытии демон жив и наблюдает, как окна исчезают одно за другим, —
`lastLayout` пустеет сам. Непустой layout, переживший перезагрузку, означает, что
машина ушла без предупреждения.

Восстановление последовательное, по одному окну:

1. запустить `wt.exe` с командой входа в сессию;
2. дождаться появления среди окон WindowsTerminal нового `id`, которого не было
   до запуска;
3. это гарантированно та сессия, которую только что запускали (запускали по
   одной), — сразу поставить окно на место; заголовка ждать не нужно.

Параллельный запуск невозможен: несколько одновременно всплывших окон не к чему
привязать. При четырёх сессиях восстановление занимает порядка полуминуты.

Триггер по умолчанию ручной: пункт трея «Restore claude sessions» и
`node src claude-wt restore`. При старте `watch` авария детектится и попадает в
лог, но ничего не запускает, пока в конфиге не выставлен `restore.auto`. Поднять
на загрузке несколько ssh-сессий — слишком заметный побочный эффект, чтобы делать
это молча.

## Конфигурация

Новый блок в `~/.config/windows11-manager.config.js`:

```js
claudeWt: {
  enabled: true,
  interval: 1000,
  stableTicks: 2,
  sessionsFile: 'V:\\.ccfzf.sessions.json',
  statePath: 'C:\\Users\\popstas\\AppData\\Local\\windows11-manager\\claude-wt.json',
  desktop: true,                    // возвращать и на виртуальный стол
  launch: {
    command: 'wt.exe',
    args: ['-w', '-1', '-p', 'popstas', 'ssh', '-A', 'popstas@pc-virt.popstas.pro',
           '-t', 'ccfzf --session {id} --kiosk'],
  },
  restore: { auto: false, windowTimeoutMs: 30000 },
}
```

Команда запуска вынесена в конфиг, а не зашита в код: она завязана на профиль
Windows Terminal и хост, и это единственное место, где claude-wt знает про ssh.
Плейсхолдер `{id}` подставляется идентификатором сессии.

## Требуемая правка в ccfzf

Неинтерактивного входа в сессию по id сейчас нет: ccfzf принимает проект и всегда
показывает интерактивный список, трейлинг-аргументы уходят в `claude`. Нужен флаг
`--session <id>`, который сразу открывает указанную сессию, а в паре с `--kiosk`
по выходу возвращает в список сессий её проекта. Отдельная небольшая правка в
репозитории `popstas/ccfzf`; без неё восстановление после краха не работает,
позиционная память — работает.

## Обработка ошибок

- **Дамп ccfzf недоступен, битый или протух** (V: не примонтирован, pc-virt
  недоступен) — работаем на собственной истории `titles`, предупреждение в лог не
  чаще раза в 5 минут. При тике раз в секунду спам в лог сам становится проблемой.
- **Окно закрылось между решением и действием** — ошибка ловится на уровне одного
  окна, цикл продолжается.
- **Сохранённая позиция вне видимой области** (монитор отключён) — bounds
  зажимаются в рабочую область ближайшего монитора.
- **Файл состояния побит** оборванной записью — переименовывается в `.bak`, демон
  стартует с чистого состояния и не падает.
- **`wt.exe` не появился за `windowTimeoutMs`** при восстановлении — слот
  пропускается, остальные продолжают восстанавливаться.

## Тестирование

Vitest по чистым хелперам, Windows под тестами не нужен:

- `indexSessions()` — коллизии заголовков, приоритет `live` и свежего `mtime`,
  пустой дамп, битый JSON;
- `step()` — новое окно с сохранённой позицией и без; смена заголовка на сессию с
  позицией, на сессию без позиции, на не-сессию; нестабильный заголовок; дребезг
  после собственного перемещения; исчезновение окна; два окна с одинаковым
  заголовком; свёрнутое окно;
- `detectCrash()` — состояние старше boot-time при непустом layout; состояние
  новее boot-time; пустой layout;
- `planRestore()` — слоты в команды запуска, подстановка `{id}`;
- `clampBoundsToMonitors()` — позиция на отключённом мониторе.

Проверка вживую — вручную на Windows, как и для остального проекта.

## Известные ограничения

- Позиция привязана к сессии, а не к проекту: новая сессия в том же проекте
  открывается там, где её оставит пользователь, и запоминается отдельно.
- Дамп ccfzf обновляется только при запуске ccfzf, поэтому заголовок, изменившийся
  по ходу уже идущей сессии, попадёт в индекс не сразу. История `titles` в
  состоянии смягчает это для сессий, которые claude-wt уже видел.
- Сессии старше 200 последних выпадают из дампа и опознаются только по
  собственной истории заголовков.
