# Модель данных claude-wt

Откуда берутся данные сессий, где они лежат по пути, как часто обновляются, и когда обычное окно Windows Terminal начинает отслеживаться.

Связка четырёх мест и грабли на границах — в [SKILL.md](./SKILL.md).

## Карта хранилищ

```
pc-virt (V:)                          Windows (локально)              Home Assistant / панель
─────────────────                     ──────────────────              ──────────────────────
~/.ccfzf.sessions.json        ──►     кэш индекса (RAM, 15 с)
  (дамп ccfzf)                        sessions.js

~/.claude/claude-wt/          ──►     кэш progress/meta (RAM, 3 с)
  <id>.state.json                     только view-слой
  <id>.status.json  ──┐               (пикер / MQTT export)
  <id>.meta.json      │
                      │ (хук сливает
                      │  числа в state)
                      ▼
                  <id>.state.json     ──►  claudeWtSessions()
                                           │
                                           ▼
                                      MQTT Discovery / HA entities
                                           │
                                           ▼
                                      openHASP (тексты)

Windows Terminal hwnd/title/bounds
  (EnumWindows, раз в interval)   ──►  liveState в RAM демона
                                           │ (при смене layout fingerprint)
                                           ▼
                                      claude-wt.json          (statePath)
                                      claude-wt.snapshots.json
```

Типичные пути в живой конфигурации:

| Что | Путь |
|---|---|
| Дамп сессий | `V:\.ccfzf.sessions.json` ← `~/.ccfzf.sessions.json` на pc-virt |
| Состояния агента | `V:\.claude\claude-wt\<id>.state.json` |
| Мета старта | `V:\.claude\claude-wt\<id>.meta.json` |
| Промежуточный статуслайн | `V:\.claude\claude-wt\<id>.status.json` (хук, не читается Windows напрямую) |
| Память позиций | `%LOCALAPPDATA%\windows11-manager\claude-wt.json` (`claudeWt.statePath`) |
| Снимки раскладов | рядом со state: `claude-wt.snapshots.json` |
| Опубликованный файл окон | `claudeWt.windowsFile`, пример: `V:\.ccfzf.sessions.claude-wt.json` — пишет демон, лежит на общем диске: читатель (ccfzf-picker) на другой машине |

## Источники первичных данных

### 1. Дамп ccfzf — канал к двум читателям, не общий снимок

**Кто пишет:** `ccfzf --dump` на pc-virt (по запросу, не непрерывно); ту же проекцию (`dump_record()`) пишет и режим `state` — иначе форма файла зависела бы от того, кто писал последним.

**Когда обновляется:**
- при каждом открытии пикера (`windows/claude-sessions-start`);
- после spawn проектного хоткея (`windows/claude-focus-project`), с задержкой 1.5 с / 4 с — файл сессии на Linux появляется не мгновенно;
- при любом ручном/скриптовом запуске ccfzf, который переписывает дамп.

**Что внутри (на сессию):** ровно восемь полей, в этом порядке — `id, title, cwd, live, mtime, kind, parent, activityAt` (`DUMP_KEEP` в ccfzf). Раньше их было тринадцать. Файл — не общий снимок состояния сессии, а канал к двум конкретным читателям (`loadSessionIndex`, `loadBackgroundAgents` в `sessions.js`), и несёт ровно то, что они читают; остальное — `gist`, `doing`, `file`, `projects`, `age`, `frozen`, `pid`, `tty`, `tmux`, `agent`, `window` и т.д. — по-прежнему уезжает, но только в полном ответе `ccfzf --state` (stdout, читателю на другой машине), не в этот файл.

Сессий внутри тоже не «до ~200»: `--limit`, умолчание **100** (было 200), и это не жёсткий срез, а объединение — `pick_files` в ccfzf берёт голову списка по свежести и добавляет к ней всех, кто вне головы, но `live` или с открытым окном (`live` уже вобрал окна раньше среза). Простой срез по времени мог бы потерять сессию, чей терминал открыт, но транскрипт давно не трогали; фильтровать вместо этого только по `live` нельзя — флаг уже однажды соврал (см. ниже), а объединение только добавляет кандидатов и потому соврать не может.

`live` и `kind` считает `running_sessions()` по `/proc`: процесс признаётся сессией по argv[0] (`claude` или путь `~/.local/share/claude/versions/*`), а вокругсессионные подкоманды (`daemon`, `bg-pty-host`, `bg-spare`, `agents`, …) отбрасываются — иначе `claude agents`, сидящий в `~`, «оживлял» бы новейшую сессию домашнего каталога. Id берётся в порядке уверенности: `--session-id` (у форка это он сам), затем `--resume` (uuid или путь к `.jsonl`), затем эвристика новейшего файла в cwd. `kind: "background"` ставится, когда родительский процесс — `bg-pty-host`, и тогда `parent` = сессия из `--resume`.

`activityAt` — отметка активности хука: mtime файла `<id>.state.json`, epoch-секунды, `int`, `floor`. Это то самое число, за которым читатель раньше ходил по сети. Писатель считает её на своей стороне одним `os.scandir` по каталогу состояний — файлы там для него локальные — и кладёт в каждую запись дампа. Читатель раньше добывал то же самое сам: `fs.statSync` по V: на каждого кандидата со спорным заголовком, 354 сетевых вызова на 200 сессий, ~1.3 мс каждый, 455 мс на сборку индекса. У обычного дампа сеть теперь не тревожится вовсе.

**Промежуточное хранение:** файл на V:. В процессе Windows — модульный кэш `loadSessionIndex`. Ключ — mtime дампа и max age **15 с** (`MAX_AGE_MS`); `progressStamp` каталога состояний в ключ входит не всегда, а только когда дамп в нём нуждается — `dumpNeedsHookStamps` в `sessions.js` смотрит, у каждой ли сессии есть свой `activityAt` (`hasHookStamp` в `sessions-helpers.js`); если да, ранжировать тёзок больше нечем, кроме самого дампа, и сетевой `stat` каталога на каждый тик демона был бы платой ни за что.

Сетевой путь остался запасным и работает по-записочно: если у конкретной записи нет `activityAt` (дамп от старой версии ccfzf), по сети опрашивается именно эта запись — решает `stampOf` в `sessions-helpers.js`. Внутри одной сборки индекса каждый id опрашивается не больше раза — памятка `memoize` в `indexSessions`.

Оборотная сторона: запись хука в каталог состояний раньше попутно двигала `progressStamp` и тем самым заставляла пересобрать индекс — бесплатный лишний повод обновиться против врущего mtime дампа на сетевом диске. Теперь, когда `progressStamp` в обычном случае не считается, худшая задержка при неизменившемся mtime дампа выросла с «до следующей записи хука» до самого `MAX_AGE_MS` — 15 с. Дефектом это не признано (комментарий в коде обещает ровно эту границу), но в модели данных ей стоит быть явной.

**Кто читает:** тик демона (привязка окна к id), `claudeWtSessions()` / `openSessionMap` (открыто ли окно).

### 2. Хуки агента — живое состояние сессии

| Файл | Кто пишет | Событие | Поля |
|---|---|---|---|
| `<id>.state.json` | `wt-progress.sh` | tool-start, attention, stop и др. хуки Claude Code | `state`, `updated`, `event`, `message`, `summary`, `lastSummary`, `summaryAt`, `turnAt`, `prompt`, `question`, плюс `costUsd` / `contextPct` после слияния со statusline |
| `<id>.status.json` | `claude-wt-statusline.sh` | каждый рендер статуслайна | `context_window`, `cost` — промежуточный буфер |
| `<id>.meta.json` | `claude-wt-agent-state.sh` | `SessionStart` | `started` (epoch sec) |

В stdin хука прогресса нет токенов и стоимости — только `session_id`, `transcript_path`, `cwd`, … Числа статуслайна перехватываются отдельно и на следующем событии сессии попадают в `state.json`. У читателя на Windows один файл на сессию.

Сводка считается на `stop`/`fail`/`attention` и, не чаще раза в `SUMMARY_TTL` (90 с), на `tool-*`: ход бывает длиной в час, и без этого строка стояла бы на позапрошлом ответе. `summaryAt` — отметка последней попытки, а не последней удачи: пустой хвост иначе читался бы на каждое событие.

Правая колонка строки на плате поделена надвое: сверху контекст (`usage`, объекты 21..25), снизу время (`time`, объекты 51..55) — высоты держат `usage_h` / `time_h` в `openhasp_lines.src.yaml`. Обе строки приходят готовыми из `slotUsage` / `slotTime` (`src/claude-wt/ha/entities.js` в windows11-manager): развилка «ход или активность» посчитана там, а не шаблоном, иначе она была бы размножена по пяти кнопкам на каждой плите.

Времени в записи три, и путать их нельзя: `updated` — последнее событие (у работающей сессии это секунды назад, каждый вызов инструмента её двигает), `started` в `meta.json` — вся сессия, `turnAt` — начало текущего хода. Последнее ставится на `start` и дальше только переносится, поэтому у отдохнувшей сессии показывает, когда начался её последний ход. Возраст в строке пикера берётся от `turnAt` у работающей и от `lastActivity` у всех прочих.

Фоновый агент пишет своё состояние сам, под своим id. Слота у него нет, поэтому view читает и файлы детей (`loadBackgroundAgents` → `activeAgent`), а строка остаётся родительской.

**Промежуточное хранение:**
- на диске — каталог `progressDir` (V:);
- в RAM процесса, который открыл пикер — кэш `loadProgress` / `loadMeta` (mtime + max age **3 с**).

**Важно:** демон в тике эти файлы **не читает** (бюджет опроса + SMB). Раньше единственным исключением был `progressStamp(dir)` — сетевой `stat` каталога состояний на каждый тик; теперь, когда дамп несёт свой `activityAt` на каждую сессию (§1), он считается не всегда, и у обычного дампа сетевого обращения нет вовсе. Точечный `activityAt` для спорных заголовков остался — но как запасной путь на одну лишённую своей отметки запись (§1), а не как правило на каждый тик.

`state` ∈ `active` | `question` | `review` | `idle`.

### 3. Окна Windows — геометрия и фокус

**Кто даёт:** ОС через `getVisibleWindowIds` → один раз `getWindowById` на новый hwnd → title/bounds только у `WindowsTerminal.exe`.

**Интервал:** `claudeWt.interval` (по умолчанию **1000 мс**).

**Промежуточное хранение:**
- `terminals` / `notTerminals` в RAM — вердикт «это терминал» на жизнь hwnd;
- `prevWindows` / `liveState` в RAM демона — рабочая структура;
- на диск (`statePath`) — только когда `layoutFingerprint` сменился (слоты / lastLayout), не каждый тик из‑за `updated`.

**Поля слота** (`slots[sessionId]`):

```jsonc
{
  "titles": ["текущий", "…история до 10"],  // новейший первым
  "cwd": "/home/…",
  "bounds": { "x", "y", "width", "height" },
  "desktop": 2,           // виртуальный стол; читается только при binding
  "focusedAt": 1785…,     // epoch sec, переход фокуса на окно сессии
  "lastSeen": 1785…       // epoch sec, трекер видел окно
}
```

Корень файла: `{ version: 1, slots, lastLayout, updated }`.

`focusedAt` ставится **только на переходе** foreground hwnd → окно с `sessionId` (не пока окно остаётся активным). Отсюда `agentSeen` в пикере: `focusedAt >= progress.updated`.

### 4. Снимки раскладов

**Кто пишет:** `snapshotTick` в том же демоне.

**Когда:** состав открытых session id устоялся `snapshots.debounceMs` (по умолчанию **60 с**); смена только координат переписывает последний снимок без нового id.

**Где:** отдельный файл рядом со state.

### 5. Опубликованный файл окон (`windowsFile`) — не только для пикера

**Кто пишет:** демон, на каждом тике (`buildWindowsFile()`, `src/claude-wt/windows-file-helpers.js`); на диск — не реже раза в `WINDOWS_FILE_HEARTBEAT_MS` (**30 с**), даже если раскладка не менялась. Это сердцебиение: свежесть читатель судит по `generated`, и без гарантированной перезаписи раз в 30 с застывшая метка была бы неотличима от «демон умер».

**Что внутри:** `host`, `pid` (демона), `generated` (секунды), `windows` (по сессии — `title`, `desktop`, `lastSeen`, `focusedAt`) и обрезанный `snapshots`.

**Поле `pid` служит двум читателям.** Изначально оно только для ccfzf-picker: Windows отдаёт передний план лишь тому, кто уже им владеет, или через `AllowSetForegroundWindow` на конкретный pid, поэтому подъём окна с панели/пикера идёт через этот pid. С переездом MQTT сюда же у поля появился второй потребитель — сторож демона (`src/mqtt/daemon-watchdog.js`, отдельный процесс от демона): он не может спросить `claudeWtStatus()` (та отвечает про демона в процессе, который спросил, а не про настоящий демон) и вместо этого читает `pid` отсюда, чтобы знать, какой процесс снять, если демон замолчал. Файл, который пишет **чужая машина** (`host` не совпадает с локальным именем), для обоих читателей — как отсутствующий: подниматься на чужой экран и снимать чужой процесс по этому pid бессмысленно и опасно.

**Кто читает:** `read_windows` в ccfzf → `ccfzf-picker` (что открыто, чей pid просить о переднем плане); `daemon-watchdog.js` в MQTT-процессе windows11-manager (жив ли демон, чей pid снять).

### 6. Сводный view для пикера / MQTT

`claudeWtSessions()` склеивает слоты + openMap + progress + meta + фоновых агентов → список с `agentState`, `agentSummary`, `agentPrompt`, `agentCostUsd`, `agentContextPct`, `agentStarted`, `agentTurnAt`, `lastActivity`, `agentSeen`, `agentBackground`, `agentSessionId`, `open`, `windowId`, …

Дальше свой MQTT-процесс windows11-manager (`src/mqtt/`, `src/claude-wt/ha/`) публикует в HA; панель openHASP читает сущности (не файлы на V:).

## Интервалы и события — сводка

| Данные | Первичное обновление | Кэш / промежуток | Кто потребляет |
|---|---|---|---|
| Каталог сессий (дамп) | Событие: dump по открытию пикера / после spawn / ручной ccfzf | RAM 15 с или смена mtime дампа; `stamp` каталога progress — только пока не у всех сессий дампа есть свой `activityAt` | Демон, view |
| `state.json` агента | Событие хука на каждом значимом шаге агента | RAM 3 с (только view) | Пикер, MQTT, панель |
| `status.json` | Рендер статуслайна | Локально на virt → сливается в state | Только хуки |
| `meta.json` | SessionStart | RAM 3 с (только view) | Сортировка oldest/newest |
| hwnd / title / bounds | Таймер ~1 Гц | RAM; диск при смене fingerprint | Демон → place / state |
| `focusedAt` | Событие: смена foreground window | В слоте → диск с fingerprint | `agentSeen`, project hotkeys |
| Desktop number | Событие: binding окна к сессии | В слоте | Place на VD |
| Snapshots | Дебаунс 60 с стабильного состава | Файл снимков | Restore last / меню |
| Опубликованный файл окон (`windowsFile`) | Тик демона (~1 Гц), запись на диск не реже раза в **30 с** (сердцебиение) | На диске | ccfzf → ccfzf-picker; сторож демона |
| Статистика окон в HA (`publishStats`) | Таймер **60 с** + разовый замер по подключению к брокеру | — | Home Assistant, топик `publishStatsTopic` |
| Опрос при появлении окна (`placeWindowOnOpen`) | Таймер **1500 мс**, свой в процессе MQTT (второй поллер рядом с демоном) | RAM | Автоматическая расстановка |
| Проверка сторожа демона | Таймер **30 с**; лечение не чаще раза в **5 мин**; молчание = запись `windowsFile` старше **90 с** (3× сердцебиения); после старта самой MQTT-службы — grace **120 с** | — | `daemon-watchdog.js` |

Перезапуск сессии под **новым id** не обновляет дамп сам по себе: пока dump не перепишут, индекс (даже с TTL 15 с) может держать старый id — окно привяжется не туда, сессия «пропадёт» из списка. Лечится dump при открытии пикера + `invalidateSessionIndex`.

## Как начинается отслеживание окна (обычный Windows Terminal)

Демон не знает про «открыли сессию» как про событие приложения. Он видит только окна.

### Шаг за шагом

1. **Появился hwnd.** На тике `getVisibleWindowIds()` находит новый id. Один раз вызывается `getWindowById`: если path — `WindowsTerminal.exe`, окно попадает в `terminals` и дальше каждый тик отдаёт title + bounds.

2. **Заголовок ещё плавает.** При входе в Claude заголовок меняется цепочкой (шелл → claude → имя сессии). Трекер копирует title, но `stableTitle` появляется только после `stableTicks` одинаковых тиков подряд (по умолчанию **2** ≈ 2 с). Пока title не устоял — слота нет, окно не двигают.

3. **Устоявший title → session id.** `resolveSession`:
   - сначала индекс дампа ccfzf (ключ — title без статус-глифа `✳`); при `ambiguous` всё равно берётся `best`;
   - иначе история `titles` в уже известных слотах (если слотов несколько — с большим `lastSeen`);
   - если два окна показывают один title — привязывается только с большим hwnd, остальные без `sessionId`.

4. **Первая привязка (binding).**
   - Слот уже есть с `bounds` → окно переносят на запомненное место (и desktop, если включено).
   - Слота нет, окно не свёрнуто → создаётся слот с текущими bounds; один раз читается номер VD.
   - Свёрнутое (`x < -10000`) слот не создаёт — позиция не пишется.

5. **Дальше каждый тик.** Пока `sessionId` держится и нет pending move: обновляются bounds (пользователь подвинул) и `lastSeen`. Смена title на приглашение шелла → `sessionId` сбрасывается при новом stable title; старый слот остаётся на диске.

6. **Догнавший дамп.** Если title устоял раньше, чем сессия попала в ccfzf dump, на следующих тиках (пока нет sessionId, но есть stableTitle) привязка пробуется снова — без перемещения окна: позиция уже считается выбором пользователя.

### Что нужно, чтобы «обычный» терминал попал в систему

| Условие | Иначе |
|---|---|
| Демон `claude-wt watch` запущен | Окна не пишутся в state |
| Процесс — Windows Terminal | Другие терминалы игнорируются |
| В окне сессия с title, который есть в дампе (или уже был в слотах) | Лог `terminal window not matched to a session`, слота нет |
| Title держится ≥ `stableTicks` | Ждём успокоения заголовка |
| Нет коллизии одинаковых title у двух окон / двух равных кандидатов в дампе | Окно не трогаем |

При одинаковом title у двух окон привязывается окно с **большим hwnd** (прокси «новее»); остальные с тем же title остаются без `sessionId`. При `ambiguous` в дампе берётся уже выбранный `best.id` — отказ от привязки больше не делается.

Отдельного API «начать трекать эту сессию» нет: достаточно открыть Claude Code в WT так, чтобы заголовок окна совпал с записью в дампе (или с уже известным слотом).
